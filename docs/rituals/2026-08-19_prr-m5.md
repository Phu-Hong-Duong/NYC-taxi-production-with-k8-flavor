## 0. What this review could NOT do, said first

1. **The champion was already serving when this review was held.** BLUEPRINT
   §9/M5 says the checklist is walked "BEFORE the champion serves"; in this
   program the deploy landed at M5-S2 and the review is the milestone's last
   story, because the kickoff sequenced it that way (S1 platform → S2 wire →
   S3 parity → S4 load → S5 review) and because three of the four boxes below
   are only fillable with numbers S3 and S4 produce. **The honest reading:**
   this is a readiness review held against a *rehearsal* deployment carrying no
   user traffic — there are no users, the endpoint is reachable only from this
   laptop, and the review is the gate on the M5→M6 boundary rather than on
   first traffic. It is minuted as a deviation, not smoothed over. **M6 is where
   the ordering bites**: the canary/shadow work will put a *challenger* on the
   wire, and that review must happen before, not after.
2. **The rollback could not be rehearsed.** M5 is legislated alias-neutral, and
   a rehearsal moves `@champion`. Box 2 is therefore about a *typed and argued*
   procedure, and it is labelled that way in the runbook, in this review, and in
   the deployments ledger.
3. **No alert can be fired here.** There is no Prometheus, no Alertmanager and
   no Grafana in this cluster — they are M6's by the kickoff's own scope list.
   Box 3 is a PLAN with named signals and named sources, which is a real
   artifact; a vague intention would not be.

### Box 2 — rollback typed ✅ (and NOT rehearsed, stated three times)

`docs/runbooks/serving.md` §4, six numbered steps: read what serves now → read
the target version's `feature_set` **from the registry** → move the alias →
move `configs/train.yaml: features.version` with it → `make serve` →
`make quote` + `make verify-m5`.

**The review's substantive finding, and it changes what a rollback IS.** A
rollback to version 1 is not a pointer move. Version 2 eats **24** features and
version 1 eats **5**; the client's matrix comes from `configs/train.yaml:
features.version`, so an alias-only rollback yields a predictor that loaded a
5-column model while every request carries 24 columns — MLflow's logged
signature refuses it and the rider gets a 500 from a system whose every
condition says `Ready`. Evidence that the two halves are really coupled, read
live from the registry:

```
=== version 1 run 3adee05a855a424bb664c7fea3735703
    feature_set = v1
    gate_floor = baseline-group-median        gate_challenger_mae = 3.2608
=== version 2 run 92b73bd4f77d4a05b92472bfcfb3cccf
    feature_set = v2
    gate_floor = baseline-group-median-od-fallback   gate_challenger_mae = 3.2403
alias champion -> 2
features cfg: {'version': 'v2', ...}
```

So the config half is **derivable, not guessable**: the version tells you which
feature set it eats. And `make verify-m5` §2 asserts exactly that coherence —
**the served version's `feature_set` tag must equal `configs/train.yaml:
features.version`** — which makes a half-finished rollback a RED gate rather
than a 500 in production. That check exists because this review went looking
for what the rollback actually requires.

Also minuted, because it is a design decision and not an oversight: step 3 is a
**raw `set_registered_model_alias` call**, not a `make` target.
`registry.promote()` refuses to move an alias without a gate `Decision` and the
`incumbent_version` that decision consulted (F-011). A rollback is a human
overriding the gate during an incident; it should look unusual, be typed by
hand and leave a commit behind. **Building `make rollback` as a gate bypass is
explicitly refused here** — M6 owns the rehearsed revert.

Un-rehearsed, and the runbook says so in a block quote, in §8's list, and in
the deployments ledger row: **these commands have never been run end to end on
this cluster.** The M4-S2 backup precedent, applied.

### Box 4 — capacity sanity ✅ (with one open recommendation)

From `automation/runs/m5-load/headline.json`, the `capacity` block, measured
across the headline window from the container's own cgroup:

```
"capacity": {
  "cpu_seconds_during_window": 78.19,   "wall_seconds": 59.764,
  "mean_cores": 1.308,                  "core_seconds_per_request": 0.3258,
  "cpu_throttled_periods_during_window": 246,
  "memory_current_bytes_after": 247111680.0,       # 236 MiB
  "memory_peak_bytes_since_container_start": 298287104.0,
  "deployment": {"container": "kserve-container",
                 "resources": {"limits": {"cpu": "2", "memory": "3Gi"},
                               "requests": {"cpu": "200m", "memory": "1Gi"}},
                 "replicas": 1}
}
```

Read: **1.31 of 2 cores at 4 req/s · 0.326 core-seconds per request · 236 MiB
of a 1 GiB request · 1 replica.** The ceiling was measured, not extrapolated
(`ramp.json`): 6 req/s = **96%** of the limit, 8 req/s = **101%** with p50
jumping 18 → 115 ms. So the honest capacity statement is **~6 requests/second
per replica for this workload and this row shape**, and the headline rate of 4
was chosen to sit under it.

**Open recommendation, routed to M6, not applied here: the CPU *request* of
`200m` understates real usage by ~6×.** 200m is what the scheduler places on
and what any autoscaler would treat as the baseline; the container really wants
~1.3 cores under the load we quote. Nothing is broken today (one node, one
replica, limits at 2 cores), and it becomes wrong the moment a second workload
competes or an HPA reads it. Changing it is a change to what is on the wire, so
it belongs in the story that owns the wire (M6's release work), with a
re-measurement after — **not in a review's diff, and not in the measurement
story that found it** (M5-S4 made the same call).

**Memory has room** (236 MiB against a 1 GiB request, 285 MiB peak since
container start) and needs no action.

## 2. The F-019 policy — the SRE half, minuted here (M5-S2's cross-reference)

M5-S2 decided F-019 (the champion raises on any request dated outside the
holiday table) with **both** halves: extend the table to 2030 *and* refuse an
uncovered date in a type. The engineering half was minuted there; **the SRE
reasoning belongs here and is this:**

- The alternative — degrade and flag — produces a **wrong quote that nobody can
  see is wrong**. It has no signature: no error, no log line an operator would
  page on, and a rider gets an ETA computed from invented holiday flags.
- The chosen behaviour produces a **countable failure with its fix in the error
  text** (`422 … covers through 2030 … make holidays HOLIDAYS_TO=<year>`), which
  is what makes signal **A-3** possible at all.
- The cost is honest and stated: **an uncovered date is a refusal, i.e. a small
  outage for that class of request**, not a slightly-wrong answer. For an ETA
  quote that trade is right — the failure is visible, bounded, attributable and
  fixable by one command. For a system where any answer beats none it would be
  the wrong trade, and that is why it is a decision rather than a default.
- **Operational consequence M6 inherits:** the table has a horizon, so the
  refusal is guaranteed to start firing one day. A-3 is not just an error
  counter, it is the horizon's smoke alarm; M6 should alert on a *rising* 422
  count long before 2030-12-31.
